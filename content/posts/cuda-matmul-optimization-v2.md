> 本文替换了 2024 年发布的《CUDA 矩阵乘法优化 V2》：原文“超过 cuBLAS 25%”的结论没有经过结果校验，已经撤回，详见下文“先撤回一个漂亮的数字”一节。

在这张 T4 上，手写 FP32 矩阵乘法已经跑到了 **29.55 ms/次，cuBLAS 是 28.96 ms/次**。这是同一组交替测试的两轮均值：算完同一对矩阵，手写版只多花约 **0.6 ms（2%）**，全部输出都通过了与 cuBLAS 的逐元素校验。

最终保留的是 v17：每个线程块算 **128×256** 个输出，用 `float4` 读 B，再把最后十个输出块沿 K 拆开，让原本空闲的 SM 也参与计算。它比 v16 少花约 9% 的时间；后来试的 128×128 版本虽然能在每个 SM 驻留两个 block，却没能更快。

实验记录：2026 年 11 月 · M = 3840，N = 3840，K = 2880 · 所有 tile 尺寸按 M×N 写，单位为输出元素。

大部分时间由于使用的GPU无ncu权限，自己手动调优过程缺少充分分析，方向上有一定随机性。

github地址：<https://github.com/bryanzhang/cuda_matmul>

总结下几个有效的优化项：

1. global memory到使用shared memory分块计算；
2. 增大单线程计算量以减少线程和线程块调度成本；
3. globalmemory coalesce io，shared memory bank-conflicts消除(包括padding,swizzle技巧,asub加载时转置)；
4. 双缓存，使用寄存器实现线程间计算io交叠隐藏延迟；
5. 微调循环展开参数(如#pragma unroll 4)提升FFMA性能，适当减少TILEK避免循环展开后寄存器使用过多；
6. 适当增大M、N方向方向减少IO(过大则寄存器使用较多且线程块同步成本高)；
7. 向量化加载指令(float4)减少指令发射和LSU压力；
8. 最后剩余执行的线程块执行优化。

super grouping在这个shape的矩阵乘法中无效、类似的在kernel函数中显示复用asub、隐式使用bsub缓存的做法也无效(寄存器使用过多反而变慢)。

总的global io量为：

$$
4MNK\left(\frac{1}{BM}+\frac{1}{BN}\right)+4MN
$$

shared memory io量为：

$$
4MNK\left[\left(\frac{1}{BM}+\frac{1}{BN}\right)+\left(\frac{1}{RM}+\frac{1}{RN}\right)\right]
$$

其中 BM×BN 是一个线程块负责的输出 tile，RM×RN 是每个线程用寄存器计算的输出块；系数 4 是 FP32 每个元素的字节数，结果的单位是字节。

在T4卡上，用roofline模型带入不同的参数基本都是compute-bound。

## 先撤回一个漂亮的数字

2024 年的[《CUDA 矩阵乘法优化 V2》](https://www.douban.com/note/865074422/)记下了用共享内存、向量加载和寄存器分块写 SGEMM 的过程。文末把手写内核的 23.72 ms 与 cuBLAS 的 29.65 ms 相比，得出吞吐高 25% 的结论。**这条结论是错的。**从 `2_vectorize` 起，旧实验没有验证输出；旧版 8×8 源码快照甚至把行优先输出 `C[M][N]` 的行跨度写成了 `K`。这个 shape 上 K=2880、N=3840，写完并不等于写对。

11 月 20 日，我修正代码，加上结果校验，重新跑了 v0–v15。naive 版是 **119.06 ms**，早期 8×8 版是 **55.90 ms**，同批次的 cuBLAS 是 **28.99 ms**，三者都通过了校验。下面的性能比较从这批数据算起。

本轮用普通 FP32 乘加计算 `C = A × B`。测试程序先将 A、B 拷入显存，用 CUDA event 计时；每次程序运行报告 100 次运算的平均值，在最后一次将全部 **14,745,600** 个输出与 `cublasSgemm` 逐元素比较。校验拒绝非有限值，允许的绝对误差是 `1e-3 + 1e-4 × |参考值|`。下文的“两轮”指两次程序运行，不是两次 kernel 启动。

## 前十五版：把数据留在哪里？

naive 版的一个线程只算 C 的一个元素。同一行 A、同一列 B 被邻居反复使用，却要由各个线程发起加载。v1 把 A、B 的小块搬进共享内存，耗时从 119.06 降到 88.58 ms。v2 到 v4 再往前一步：把部分和留在寄存器里，让同一份输入参与多个输出的乘加。每线程从 2×2 算到 4×8，v4 到了 48.94 ms。`float2`/`float4` 减少了加载指令，但这几步还同时改变了数据复用，收益不能只记在向量化名下。

v5 是第一次反例。把四个 4×4 小块拼成 8×8，本来想再省几次搬运，结果从 48.94 退回 55.90 ms，记录中每线程用了 208 个寄存器。v6 缩短 K 方向的块仍未扭转局面；v7 保留 8×8 输出、去掉分段拼算，把寄存器降到 128 个，才到了 41.13 ms。v8 对 A 在装入共享内存时转置，配合交错访问后到 **33.71 ms**。它的 128×128 输出块，后来成了检验“双 block 驻留”想法的起点。

继续放大 tile 也有代价：v9 的 256×256 让寄存器溢出，耗时一下变成 242.20 ms。v11 改用 512 个线程分担一个 128×256 tile；v12 为当前和下一片 K 各留一套共享内存；v13 把预取拆成几段，让下一片的全局加载与当前片的计算重叠。到 v14，耗时为 32.76 ms。v15 把所有预取一口气提到前面，反而慢到 33.56 ms。于是后面的工作从 v14 分支出发。

**校正记录：v0–v15 的逐版结果（ms/次）**

| 版本 | 主要变化 | 耗时 |
|---|---|---|
| v0 / v1 | naive / 共享内存分块 | 119.06 / 88.58 |
| v2 / v3 | 每线程 2×2、float2 / 每线程 4×4、float4 | 69.77 / 50.33 |
| v4 / v5 | 4×8 复用 asub / 四个小块拼作 8×8 | 48.94 / 55.90 |
| v6 | TILE_K 缩到 16 / 再调整 asub 行宽 | 54.97 / 53.73 |
| v7 / v8 | 8×8 寄存器块 / 装载时转置与交错访问 | 41.13 / 33.71 |
| v9 / v10 | 256×256 严重溢出 / 128×256、分段复用 asub | 242.20 / 39.99 |
| v11 / v12 | 512 线程分担输出 / 共享内存双缓冲 | 36.14 / 35.20 |
| v13 / v14 / v15 | 分段预取 / 用 float4 加载 A / 集中预取 | 33.02 / 32.76 / 33.56 |

## v16：冲突消失了，毫秒数没动

v14 留下了一个很具体的问题：从全局内存读 A 已经能用对齐的 `float4`，但把四个分量转置写到 `asub` 时，每条标量写入都有二路 bank 冲突。能否保持加载方式，只改这一步的地址？

按 4 字节的 float 编号，T4 的 bank 号为地址模 32。`asub` 行跨度为 132，所以 `asub[4*lx+c][ly]` 对应 `(16*lx + 4*c + ly) % 32`。对于同一个分量 `c`，`lx=0` 和 `lx=2` 落入同一组八个 bank，1 和 3 也一样。解决办法是只在 `lx=2,3` 时翻转列号的第 3 位，把两对重叠的地址各错开八个 bank：

```cpp
// 写入：lx = 0、1 保持原位，lx = 2、3 将列号异或 8
int col = ly ^ ((lx >> 1) << 3);
asub[buf][4 * lx + c][col] = component;

// 计算：以 8 个 float 为一组换位，组内两次 float4 读取仍然对齐
int acol = 8 * (ty ^ (j >= 8));
// 从 asub[cur][j][acol] 和 [acol + 4] 读取
```

逐 warp 枚举地址，写入从每个 bank 对应两个不同的字变为一个；寄存器从 126 降到 124，没有溢出。可是在交替对照中，v14 为 **32.39–32.77 ms**，v16 为 **32.74–32.76 ms**。单测这组共享内存写入，新旧映射也都是 128 个周期一轮。这里能确认的是地址冲突已消除、总耗时未见改善；机器未开放 Nsight Compute 性能计数器，不能把地址推导说成计数器实测，更不能推论所有二路冲突都免费。

## v17：比改 bank 更有用的是填满最后十块

v17 保留 v16 的布局，再改两件事。第一件在内层循环：让一个线程负责的八列变成两组连续四列，每个 K 步读 B 就从八条标量共享内存加载变成两条 `LDS.128`。普通输出 tile 写 C 也能用 `float4`。第二件在网格层面：只拆分最后没填满一波的 tile。

**为什么只拆十块？** 输出正好是 (3840/128) × (3840/256) = 30 × 15 = **450 个 tile**。T4 有 40 个 SM，此版本每个 SM 可驻留一个 block。前 440 个 tile 填满十一波；余下十个若仍各交给一个 block，最后就只有十个 SM 有活干。

对这十个输出 tile，每个沿 K 切四份。原来一个 block 走完 180 个 K 步，现在四个 block 各走 45 步，正好生成 40 个尾部 block。于是实际发射 **440 + 40 = 480** 个 block，输出仍是 450 个 tile。只有尾部输出预先清零并用 `atomicAdd` 合并；这笔开销也计入了耗时。

**先拆开测，再合起来测 · T4，ms/次**

| 版本 | 相对 v16 的变化 | 第一轮 | 第二轮 |
|---|---|---|---|
| v16 | 起点 | 32.76 | 32.73 |
| v17a | 只改 B 的读取与 C 的写回 | 31.76 | 31.45 |
| v17b | 只做尾波 split-K | 31.32 | 31.31 |
| v17c | 合并两项，未显式指定外层展开倍数 | 30.78 | 30.80 |

尾波拆分还有个副作用：同一个 kernel 要跑 180 或 45 步，循环次数不再是编译期常数。另一组对照里，合并版耗时 30.53–30.78 ms，显式展开两次为 29.91–29.92 ms，**展开四次为 29.73–29.76 ms**。配上 `__launch_bounds__(512, 1)`，编译结果为每线程 128 个寄存器、零溢出。这一版作为 v17 提交。和约 32.75 ms 的 v16 相比，典型耗时减少约 9%。

提交前的一次完整校验中，14,745,600 个元素超出容差的数量为 0，最大绝对误差为 0.00317。尾块的部分和改变了 FP32 加法顺序，所以这里的 PASS 是数值容差内一致，不是与 cuBLAS 逐位相同。

## 回到 v8 的 128×128：两个 block 能赢一个吗？

为了让每个 SM 同时放下两个 block，v18 回到 v8 的 16×16 线程，每线程仍算 8×8 个输出。A、B 都双缓冲，去掉 padding 后每个 block 恰占 `2 × 16 × (128 + 128) × 4 = 32 KiB` 共享内存。T4 在 64 KiB 共享内存配置下能放两个；实际调用 CUDA occupancy API 返回的上限也是 **2 blocks/SM**。这验证了可驻留容量，不是每个时刻的活跃 block 计数。

现在输出有 30×30 = 900 个 tile；按 80 个驻留位置计算，最后 20 个也可以各沿 K 拆成四份。关键在于：**两个 256 线程 block 和一个 512 线程 block，合计都是 16 个 warp/SM。** 双驻留提供了两个可以独立同步的 block，却没有把可调度 warp 数翻倍。小 tile 还有代价：每个 16 宽的 K 步，计算量除以 A、B 的加载字节数，从 128×256 时的 42.7 降到 128×128 时的 32 FLOP/byte。这是按块计算的复用量，不是实测 DRAM 带宽。

**最后一次交替对照 · 每格为 100 次运算的平均耗时（ms），各轮均 PASS**

| 版本与布局 | 输出 tile | 第一轮 | 第二轮 |
|---|---|---|---|
| v17 · 已提交 | 128×256 | 29.48 | 29.78 |
| v18_u1 · 每 warp 装 A 的 8 行，各 4 个 float4 | 128×128 | 30.29 | 30.01 |
| v18e_u1 · 16 行，各 2 个 float4 | 128×128 | 30.90 | 30.59 |
| v18f_u1 · 同 e，warp 内改为 4×8 布局 | 128×128 | 31.58 | 31.37 |
| v18f_u4 · 同 f，K 循环展开四次 | 128×128 | 31.62 | 31.30 |

u1、u4 是外层 K 循环的展开倍数。不要拿不同轮次的最小值相减：最快的 v18_u1 在两轮中分别比同期 v17 慢 0.81 和 0.23 ms。

还有一个没有进入最后一表的反例：让 32 个 lane 分别从 A 的不同行取一个 `float4`，不用 swizzle 就能无冲突地写回 asub，编译也没有寄存器溢出。但每条全局加载涉及 32 个 32B sector，每个只用 16B；此前的合并映射只需 16 个 sector。这个版本跑出 33.92–33.94 ms。**局部内存零溢出、共享内存零冲突，都不能替代整段运行时间。**本次测过的 v18 没有胜出，保留 v17 即可。

## 与 cuBLAS 对表，以及最后一个没赚到的优化

v5 在一个 block 内复用四个小块，和 Triton 的 super grouping 有什么区别？前者是同一个 block 再用一次共享内存里的数据；后者（grouped program ordering）改变不同输出 tile 的编号顺序，让相邻调度的 block 更有机会在 L2 中复用同一片 A 或 B。**提交的 v17 用行优先 tile 编号，没有跨 block 的 super grouping。**

**同一组实验中的 tile 顺序与库基线（ms/次）**

| 方案 | 第一轮 | 第二轮 |
|---|---|---|
| v17，行优先 | 29.76 | 29.34 |
| 每组 4 行，组内按列遍历 | 29.52 | 29.85 |
| 每组 8 行，组内按列遍历 | 29.82 | 29.82 |
| cuBLAS SGEMM | 28.93 | 28.98 |

4 行分组一轮赢、一轮输，8 行也没有优势。分组版还把尾部清零拆成了多次调用；这些是端到端的计时，不能单凭它们推断 L2 命中率。能落笔的结论只有两个：这一形状下分组没有稳定收益；以这两轮均值比较，v17 约 29.55 ms、cuBLAS 约 28.96 ms，手写版慢约 2%。

Nsight Systems 识别出的库内核是 `volta_sgemm_128x64_nn`，其 100 次 kernel 执行的中位数为 28.90 ms。它使用 30×60 的网格、每 block 128 个线程、每线程 122 个寄存器和每 block 12,544 字节静态共享内存。名字里的 `volta` 并不改变实际硬件是 T4 的事实。这个 trace 给出了库的启动配置；至于那半毫秒究竟来自分块、调度还是访存，单靠名字分不出来。

作为量级检查，这次运算是 `2MNK ≈ 84.93 GFLOP`，29.48 ms 对应约 **2.88 TFLOP/s**。按采样中常见的 585 MHz 估算，40 个 SM 的 FP32 理论吞吐约 3.00 TFLOP/s，对应约 28.36 ms。但采样也见过更高频率，这个数只用于核对量级，不是实测时钟恒定时的硬下限。

**收工时留下的版本是 v17。** 从校正后的 119.06 ms 到约 29.5 ms，吞吐约为起点的四倍。真正挣回最后几毫秒的，是把 B 的八次读变成两次、让最后十个 tile 也能用满 SM，以及找回 split-K 后丢掉的循环展开。消掉 bank 冲突、增加驻留 block、调整 tile 顺序，则各自回答了一个同样有用的问题：哪些地方做到“看上去更好”，在这张卡上却不值得继续改。

## 剩下的 0.6 ms：小 tile 能否少等一会儿？

下次若要继续追 cuBLAS，我会先试它给出的线索：`volta_sgemm_128x64_nn` 用的是 **128×64 的小 tile，每个 block 只有 4 个 warp**；v17 的一个 block 有 16 个 warp。v17 的主循环每换一片 K 都要执行 `__syncthreads()`。先到的 warp 得等同一 block 里最后一个 warp 到齐，哪怕只剩一组数据还没搬完。

我的猜想是，小 block 每次只需等 4 个 warp；如果同一 SM 上还有其他 block，它们也能在这段等待时间里发射指令。这样，块内同步暴露出来的等待时间可能更短。但小 tile 同时会减少数据复用，v18 就吃过这个亏。Nsight Systems 确认了 cuBLAS 的内核名和启动配置，**还没有证据把这 0.6 ms 归因于同步**。

验证时可以做一个 128×64、128 线程的版本，仍让每线程算 8×8，保留 v17 的向量访存和双缓冲。先在整波网格下比较主循环，排除尾波 split-K 的影响，再回到原始尺寸与 v17、cuBLAS 交替计时。若能取得性能计数器，就同时看等待屏障而无法发射的周期占比：小 tile 是否更快、若更快是否真的因为少等了屏障，是两个值得分开回答的问题。
